# 관리자 2단계: 전역 접속 제한

MVC 인증·채팅·게임 스트림에 공통 접속 제한을 구현했다. Spring Security 역할 권한을 사용하지 않고 1단계 DB 기능 권한과 기존 BFF·JWT·Redis·브라우저 증명을 유지한다. 관리자 화면과 Next.js BFF에서 접속·가입 제한을 편집하고 접속 허용 권한을 번호 목록으로 선택한다.

## 동작

- ROOT는 설정 목록과 관계없이 접속한다. 나머지는 최고 관리자가 지정한 역할만 예외다. ADMIN/MANAGER도 자동 예외가 아니다.
- 제한을 켜면 예외 외 기존 세션을 서버 인증에서 무효화하고 신규 로그인·토큰 갱신·활동 연장·채팅 티켓 발급/소비를 차단한다.
- 제한 중 예외를 제거하면 해당 역할의 기존 로그인도 종료한다. 제한 해제나 나중의 예외 추가로 이전 세션이 복구되지 않는다. 허용 대상이 된 사용자는 새 비밀번호 인증으로 로그인한다.
- 예외 역할과 최고 관리자의 세션은 유지한다. 임시 정책 반영 장애는 503으로 구분하고 세션 만료로 처리하지 않는다.
- 회원 역할 변경과 최초 최고 관리자 지정 시 기존 로그인을 종료한다. 동일 역할로의 요청은 종료하지 않는다. 비활성 계정의 차단 표식은 수정하지 않는다.
- 회원가입 제한은 로그인 제한과 독립된 `signUpRestricted`로 관리한다. 제한 중 가입 API는 `SIGN_UP_RESTRICTED/403`과 고정 안내를 반환하며 기존 회원의 로그인 정책은 바꾸지 않는다.

## API

기존 BFF 인증·브라우저 증명·ADMIN_ACCESS와 아래 기능 권한이 필요하다. 브라우저에서 토큰을 직접 보내는 공개 API를 추가하지 않는다.

| 메서드 | 경로 | 기능 권한 |
|---|---|---|
| GET | /api/admin/access-policy | ACCESS_POLICY_READ |
| PUT | /api/admin/access-policy | ACCESS_POLICY_UPDATE |
| PUT | /api/admin/access-policy/exemptions | ACCESS_EXEMPTION_UPDATE: 최고 관리자 전용 |
| GET | /api/admin/access-policy/roles?page=1&size=10 | ACCESS_EXEMPTION_UPDATE: 최고 관리자 전용 |

제한 스위치·문구 변경:

```json
{"enabled":true,"signUpRestricted":true,"message":"서버 점검 중입니다. 오전 3시에 다시 접속해 주세요.","expectedVersion":0,"reason":"정기 점검"}
```

예외 역할 변경:

```json
{"roleCodes":["ADMIN","EVENT_OPERATOR"],"expectedVersion":1,"reason":"점검 담당자 지정"}
```

응답은 enabled, signUpRestricted, message, exemptRoleCodes, exemptRoles, version, changedAt을 제공한다. exemptRoles는 선택한 역할의 이름·코드·기본 정보를 포함해 다른 페이지의 선택도 즉시 표시한다. changedAt은 Asia/Seoul 기준이다. ROOT는 항상 허용하므로 목록과 집계에 넣지 않는다. 역할 수는 고정하지 않으며 등록된 역할을 지정한다. 예외로 지정한 역할은 목록에서 먼저 해제한 뒤 삭제할 수 있다.

권한 번호 조회는 query(최대 100자), page(1 이상), size(10/20/30/50)를 받는다. ROOT 제외·전체 집계·마지막 페이지 보정을 DB에서 수행하며 한글은 UTF-8 이름에만 비교한다. 선택 집합은 검색·페이지·표시 개수와 분리한다. 페이지 번호는 목록 아래 중앙, 선택 요약은 오른쪽에 두고 좁은 패널에서는 두 영역을 위아래로 재배치한다.

안내는 공백만 있는 값·300자 초과·제어 문자를 거절한다. reason은 선택이며 300자 이하다. expectedVersion은 필수이고 오래된 편집은 409다. 스위치 API에는 예외 역할 입력 필드가 없으므로 위임 관리자는 자신의 역할을 추가할 수 없다. 예외가 아닌 관리자가 제한을 켜면 본인도 종료된다.

## 저장·동시성·복구

V12는 tbl_access_policy, tbl_access_policy_exemption, tbl_access_policy_revocation을 추가한다. 기본 제한은 OFF, 예외 역할은 없다. 기존 회원·게임·채팅 데이터를 삭제하지 않는다.

V31은 sign_up_restricted를 기본 FALSE로 추가한다. 가입은 같은 ROOT 공유 잠금을 가입 트랜잭션 완료까지 유지한다. 제한 변경은 ROOT 쓰기 잠금으로 진행 중 가입의 완료를 기다리고, 저장 이후 시작하는 가입은 최신 DB 설정으로 거절한다. 차단 시에는 회원 중복 조회·비밀번호 해시·저장보다 먼저 종료한다. 가입 제한은 Redis의 로그인 집행 계약에 필드를 추가하지 않는다.

1. 역할 편집과 같은 ROOT 역할 행의 쓰기 잠금을 얻고 현재 권한·버전을 재확인한다.
2. Redis 정책을 pending으로 전환해 DB 변경 도중 이전 정책으로 접속을 허용하지 않는다. 유효한 기존 최고 관리자 세션은 유지한다.
3. 설정·역할별 폐기 경계·감사 기록을 같은 MySQL 트랜잭션으로 저장한다.
4. 커밋 후 별도 트랜잭션에서 같은 잠금을 얻어 확정된 최신 정책 전체를 원자적으로 Redis에 반영한다. 다중 서버도 이 순서를 따른다.
5. 커밋/발행 실패로 남은 pending은 5초 주기 복구가 확정된 DB 원본으로 복원한다. 시작 시에도 동기화하며 최초 동기화 실패는 시작 실패로 처리한다. 정책 키/필드 유실·손상은 503으로 인증을 보류하고 재구성한다.

세션에는 발급 역할·정책 버전을 저장한다. 역할별 폐기 경계보다 오래된 세션은 제한 해제 후에도 무효다. 역할 삭제 후 같은 코드를 다시 만들어도 경계를 보존한다. 버전은 19자리 십진 문자열로 비교해 Lua 정수 정밀도 제한을 피한다. 전체 사용자 세션을 순회하지 않아 일괄 차단 비용이 사용자 수에 비례하지 않는다.

비밀번호 검증 후 짧은 발급 구간만 SQL 공유 잠금을 사용한다. 여러 로그인은 병렬 진행하고 정책·역할·계정 상태 변경과 발급 순서를 맞춘다. 세션 생성·조회·갱신·활동과 채팅 티켓의 검사는 해당 Lua와 함께 원자적으로 실행한다.

DB 저장 후 집행 확정을 완료하지 못하면 ACCESS_POLICY_UNAVAILABLE/503이다. 이때 변경이 이미 DB에 저장되었을 수 있으므로 GET으로 버전을 다시 확인한다. 이전 버전으로 무조건 재시도하거나 성공으로 표시하지 않는다.

## 연결 종료와 안내

- 정책 확정 시 Pub/Sub에는 정보 없는 버전 신호만 전달한다. 구독자는 원본을 재확인한다. 채팅은 4401/ACCESS_RESTRICTED로 종료한다.
- 알림 유실 시 공용 채팅은 약 5초, 방 채팅·게임 SSE는 약 2초 주기 검사로 종료한다. 네트워크/저장소 지연은 추가될 수 있다. 채팅 방송 전달 직전에도 세션을 확인한다.
- SSE 구독에도 최초 인증의 세션 ID를 결합한다. 대국 종료 후 처리는 기존 연결 끊김·재접속/마감 규칙을 따르며 방 강제 종료 기능을 추가하지 않는다.
- ACCESS_RESTRICTED/401은 관리자가 작성한 문구를 전달하고 자동 토큰 갱신을 반복하지 않는다. BFF는 이 코드에만 길이·제어 문자 검사를 통과한 동적 안내를 허용한다. 다른 오류는 기존 고정 메시지를 유지한다.
- 브라우저는 제한 응답 수신 시 계정 표시를 비운다. 로그인 화면에는 저장된 안내나 실패 문구를 중복 표시하지 않고 실제 로그인 요청이 차단된 때 확인창 한 곳에서 관리자 문구를 평문으로 표시한다. 저장 전후에도 안내의 앞뒤 공백을 바꾸지 않는다. 페이지 이동을 위해 문구만 sessionStorage에 최대 15분 보관하고 정상 로그인/세션 확인 후 지운다. 인증 정보는 저장하지 않는다.
- 회원가입 화면에는 로그인 차단 문구를 표시하지 않는다. 가입이 제한되면 "현재 회원가입이 제한되어 있습니다. 잠시 후 다시 시도해 주세요."를 표시한다. 가입 차단 문구 입력란은 제공하지 않는다.
- 연결이 없는 탭의 화면은 기존 30초 세션 확인 또는 탭 복귀 시 갱신한다. 서버 차단은 화면 갱신을 기다리지 않는다.

## 적용 범위

2026-10-28 개선은 실제 서비스 DB를 변경하지 않고 별도 임시 MySQL 8.4에서 V31·한글 검색·65개 역할 집계·동시 가입을 검증했다. 서버 검증 17개와 Chrome·Edge의 모의 API 브라우저 검증을 통과했으며 임시 테스트 소스는 삭제했다. 브라우저별 실행 범위는 [운영 설정 검증 기록](../../.codex-artifacts/operations-settings/verification.md)에 남긴다. 이 변경을 적용할 때는 MVC 서버와 프론트를 함께 갱신하고 V31을 적용한다. 채팅의 기존 Redis 계약은 유지한다.

이번 작업은 실제 local/dev/prod DB에 V12나 admin 최초 배정을 실행하지 않았다. 별도의 임시 MySQL 8.0.37·Redis에서 검증했다. 배포 때 MVC·chat·front를 함께 갱신하고 같은 Redis DB를 사용한다. 양 서비스의 gate.lua v1 계약은 동일하다. 기존 세션에는 정책 필드가 없으므로 첫 배포 시 다시 로그인해야 한다. 최초 관리자 지정은 [1단계 안내](authorization-stage1.md)를 따른다.

기존 인증과 같이 단일 Redis primary의 다중 키 Lua를 사용한다. Cluster나 과거 스냅샷 복원/자동 failover 도입 시 인증 상태의 일관성·지속성을 별도로 설계해야 한다. 과거 Redis 인증 데이터를 복원할 때는 모든 로그인 세션을 무효화하고 DB 정책을 재동기화해야 한다.

[검증 기록](../../../artifacts/admin-development-stage2/verification.md)에 실행 증거를 남긴다. 전체 서비스와 실제 브라우저를 함께 띄운 종단 간 검증은 이번 단계에 포함하지 않았다. 프론트 오류/세션 모듈 실행 검증과 Next.js 배포 빌드를 수행했다.

설계 참고: [Redis Lua 원자 실행](https://redis.io/docs/latest/develop/programmability/eval-intro/), [Spring 트랜잭션 처리 단계](https://springframework.org/spring-framework/reference/7.1/data-access/transaction/event.html). 설치된 Next.js 16.4.2 인증 가이드도 확인했다.
