# 관리자 8단계: 운영 대시보드·서비스 상태

## 화면·권한

- `/admin/dashboard`: 현재 접속·오늘 신규회원 두 카드와 접속 현황 그래프. 기존 `ADMIN_ACCESS`와 `DASHBOARD_READ`를 검사한다.
- `/admin/service-status`: 로그인·게임·채팅의 상태와 확인 시각. 기존 `ADMIN_ACCESS`와 `SERVICE_STATUS_READ`를 검사한다.
- `GET /api/admin/dashboard?period=TODAY|WEEK|MONTH`, `GET /api/admin/service-status`만 제공한다. 메인 서버의 요청 필터·인터셉터·서비스에서 현재 DB 권한을 확인한다. 별도 Spring Security 역할 기능을 쓰지 않는다.
- 프론트와 BFF는 기간·응답 필드·KST 구간·정수/누락 구분을 검증하고 다른 기간의 응답을 현재 그래프에 표시하지 않는다. 성공 응답은 `no-store`다. 권한이 없는 메뉴는 조회 요청을 보내지 않는다.

## 사용자가 선택한 접속 기준

현재 접속은 **최근 60초 안에 인증된 접속이 확인된 로그인 회원 수**다. 같은 회원의 여러 탭은 하나로 센다. 브라우저가 닫히거나 접속 확인이 끊기면 Redis 서버 시계 기준 60초 후 집계에서 빠진다. 화면은 보이는 동안 30초마다 갱신하므로 표시에는 마지막 조회 이후의 갱신 간격이 더해질 수 있다.

기존 모든 페이지의 `GET /api/auth/session` 확인 주기를 재사용한다. 홈 전용 공용 채팅 연결과 집계를 분리했고 기존 채팅 연결 범위를 바꾸지 않았다. 세션 확인 컨트롤러는 검증된 회원 번호만 `SitePresenceService`에 전달한다. 익명 회원·접속 IP·세션 원문·회원별 방문 이력은 이 지표에 저장하지 않는다. 접속 지표 갱신은 로그인 세션/토큰 수명을 연장하지 않으며 집계 오류가 인증 확인을 실패시키지 않는다. 백그라운드 문서는 기존 인증 확인 주기에 따라 최근 확인 구간에서 제외될 수 있다.

Redis는 기존 서버·논리 DB를 사용한다. `site:presence:{site-online}:` 접두사 아래 회원 리스 ZSET·초기화 시각·분별 최대값 HASH·미저장 분 순서 ZSET·마지막 관측 시각만 사용한다. Lua의 한 원자적 관측으로 중복 제거·만료 정리·최대값 갱신을 처리하며 관련 키는 같은 Cluster 슬롯이다. 처음 초기화한 뒤 60초는 아직 재확인되지 않은 회원을 0명으로 표시하지 않고 **집계 중**으로 표시한다.

## 추이 수집·저장

- **오늘:** KST 오늘의 시간별 최대 동시 접속.
- **7일/30일:** 오늘을 포함한 KST 날짜별 최대 동시 접속.
- 새 회원의 접속 확인 때마다 최대값을 보존한다. 타이머의 순간 샘플만으로 최대값을 추정하지 않는다. 분 경계에서 유효했던 리스가 첫 관측 전에 만료돼도, 정리 전에 경계 시각의 접속 수를 복원해 최대값을 보존한다. 한 리스보다 긴 미관측 구간은 임의로 복원하지 않는다.
- `ConnectionSampleCollector`는 관리자 화면 접속과 무관하게 30초마다 최대 120개의 미저장 분을 읽고 MySQL에 저장한다. SQL 커밋 후 읽은 값과 여전히 같은 Redis 항목만 제거한다. 그 사이 더 높은 최대값이나 새 관측이 생기면 다음 수집에 남긴다.
- V19의 `tbl_admin_connection_sample`에는 UTC 분 시작·최대 회원 수·실제 마지막 관측 시각만 저장한다. `INSERT ... AS incoming ... ON DUPLICATE KEY UPDATE GREATEST(...)`로 다중 인스턴스·재수집·응답 유실에서도 더 큰 값이 줄지 않는다. 회원 식별자는 이 테이블에 없다.
- 저장 실패 시 Redis 미저장 항목을 남긴다. 이미 수집되지 않은 과거 구간은 0으로 채우거나 그래프 선으로 이어 붙이지 않는다. 아직 기록이 없으면 집계 중, 조회 실패는 확인 불가, 마지막 실제 관측이 90초보다 오래되면 집계 지연을 표시한다. 미래 시간은 만들지 않는다.
- 기존 회원 생성 시각은 그대로 둔다. 오늘 신규회원은 KST 날짜 경계를 기존 JPA 감사 시각의 JVM 저장 시간대로 변환해 조회한다. 탈퇴/비활성화 여부와 관계없이 해당 날짜에 생성된 회원 수다. V19가 `tbl_user.created_at` 인덱스를 추가한다.

## 서비스 확인

회원 가입·실제 로그인·게임 입장·대국·채팅 메시지를 만들어 시험하지 않는다. 서비스 처리에 필요한 운영 연결을 읽기 전용으로 확인한다.

| 서비스 | 확인 대상 |
| --- | --- |
| 로그인 | 회원/역할 DB 읽기, Redis PING, 접속 정책 스냅샷 준비 상태 |
| 게임 | 게임/모드/방 DB 읽기, 입장 처리와 공유하는 Redis 연결 |
| 채팅 | chat 서버에서 메시지 저장소 읽기, Redis PING, Kafka 관리 확인, 기존 방송 파티션 준비 상태 |

정상 응답이 1초 미만이면 정상, 성공해도 1초 이상이면 지연, 확인된 의존성 실패는 장애다. 정책 반영 중은 지연이며, 아직 확인하지 않았거나 원격 상태를 가져오지 못했거나 90초 이상 지난 확인은 확인 불가다. 의도적인 로그인 제한·게임 숨김/점검 설정을 장애로 판단하지 않는다. 연결 확인은 실제 모든 업무 시나리오의 성공을 보증하는 종합 거래 테스트가 아니다.

상태는 메인 서버에서 30초 간격으로 수집하고 관리자 요청은 권한 확인 후 결과를 읽는다. 관리자 수에 비례해 DB/브로커 점검을 반복하지 않는다. 집계와 점검은 `adminMonitoringScheduler`의 별도 두 스레드를 사용한다. `defaultCandidate=false`로 기존 기본 스케줄러와 대국 시계 설정을 대체하지 않는다. DB 점검 SQL에는 2초 제한을 적용한다.

채팅 상태는 `/internal/admin/chat/health`라는 고정 GET 한 경로를 추가했다. 7단계의 10초 일회용 증명·정확한 경로 해시·GETDEL 소비를 재사용하며 메시지용 증명을 상태 확인에 재사용할 수 없다. 쿼리·브라우저 Origin·비정규 경로·쓰기 요청은 거절한다. chat 서버는 WebFlux 스레드를 블로킹하지 않고 4초 제한으로 확인하며 결과를 10초 공유한다. 외부에는 `state`·`checkedAt`만 전달하고 인프라 주소·세부 오류·자격 증명은 노출하지 않는다.

## 반영

프론트·back·chat을 함께 반영하고 두 서버를 재시작한다. 메인 서버 시작 시 기존 Flyway 설정으로 **V19**를 적용한다. 새 Redis 서비스나 새 환경 변수는 필요하지 않다. 채팅 서비스 상태 확인은 7단계와 같은 `CHAT_ADMIN_ORIGIN` 설정을 사용한다. local은 현재 WebSocket 주소의 호스트/포트, dev/prod는 명시한 내부 주소를 사용하며 prod는 신뢰되는 HTTPS여야 한다. 내부 경로를 공개 프록시에 추가하지 않는다.

최초 반영 시 이전 기간을 가상의 수치로 소급 생성하지 않는다. 접속 카드는 초기 60초 준비 후 표시하고 그래프는 실제 관측·저장이 시작된 구간부터 채워진다. 현재 접속·신규회원·추이의 장애는 각각 구분한다.
