# 관리자 5단계: 유저 관리와 본인 닉네임 변경 이력

## 제공 기능과 권한

`/admin/users`에서 회원 그리드·상태/권한 필터·상세 모달·권한에 따른 개인정보 원문·본인 닉네임 변경 이력을 제공한다. 계정 관리 탭은 실행 가능한 기능 권한이 있는 사용자에게만 보인다. 역할 종류나 회원 수를 화면 코드에 고정하지 않는다.

| API | 필요 기능 | 동작 |
| --- | --- | --- |
| GET `/api/admin/users` | USER_READ | 아이디/닉네임 앞부분 또는 회원 ID 검색, 상태·역할·번호 페이지 |
| GET `/api/admin/users/role-options` | USER_READ | 검색·커서 방식의 역할 이름/코드. 기능 권한·회원 수는 제외 |
| GET `/api/admin/users/{id}` | USER_READ | 기본 회원 정보. 개인정보 필드는 포함하지 않음 |
| GET `/api/admin/users/{id}/nickname-history` | USER_READ | 저장된 변경 전/후·시각·본인 변경 표시, 번호 페이지 |
| GET `/api/admin/users/{id}/sensitive` | USER_READ + USER_SENSITIVE_READ | 별도 사유 입력 없이 열람 감사 저장 후 개인정보 원문 반환 |
| PUT `/api/admin/users/{id}/status` | USER_READ + USER_STATUS_UPDATE | ACTIVE/INACTIVE 변경, 버전·사유·감사 기록 |
| POST `/api/admin/users/{id}/sessions/revoke` | USER_READ + USER_SESSION_REVOKE | 계정 상태를 유지하고 기존 로그인 세션 종료 |
| GET/PUT `/api/admin/users/{id}/role` | USER_ROLE_UPDATE (현재 SUPER_ADMIN 전용) | 기존 역할 배정 API 사용. UI는 검색 가능한 단일 역할 선택과 확인·사유 입력 제공 |

조회 기본은 탈퇴 제외이며 `status=DELETED`를 명시하면 탈퇴 회원도 조회할 수 있다. 상태 필터는 ACTIVE/INACTIVE/PENDING/DELETED, 역할 필터는 임의의 등록 역할 코드다. 회원 목록과 닉네임 이력은 `page`(1부터, 기본 1)·`size`(10/20/30/50, 기본 10)를 받는다. 같은 필터의 집계와 해당 번호의 행만 조회하고 `page`, `size`, `totalPages`, `totalElements`를 반환한다. 범위를 벗어난 페이지는 실제 마지막 페이지로 보정하며 빈 목록도 1페이지다. 회원 집계에는 역할 조인을 하지 않는다. 검색의 %, _, !는 와일드카드로 취급하지 않는다. 기본 컬럼의 B-tree 인덱스를 활용하는 앞부분 검색과 3초 쿼리 제한을 사용한다. 역할 선택기 등 기존 다른 목록의 커서 계약은 유지한다.

모든 관리 API는 기존 BFF 인증·JWT/Redis·브라우저 키·현재 DB 관리자 기능 권한 검사를 유지한다. UI가 숨겨져도 서버가 기능 권한을 검사한다. Spring Security 역할 authority를 추가하지 않았다.

## 본인 닉네임 변경 이력

사용자 결정에 따라 **본인만 닉네임을 변경**하며 관리자는 이력만 읽는다. 관리자 닉네임 편집 API/입력은 제공하지 않고 임의 필드 끼워넣기도 BFF에서 거절한다.

기존 `UserProfileService.updateNickname`의 회원 행 잠금 안에서 기존 이름을 읽고, 새 닉네임과 `tbl_user_nickname_history`의 스냅샷을 같은 트랜잭션으로 저장한다. 동일 이름 저장은 변경·이력·채팅 프로필 알림 세대를 만들지 않는다. 이력 저장 실패는 닉네임과 편집 버전도 롤백한다. 두 요청이 동시에 변경해도 직전 이름 → 다음 이름의 연결이 보존된다. 채팅 프로필 통지는 기존 커밋 이후 경로를 유지한다.

이력은 실제 변경만 추가하는 불변 엔티티이며 회원 ID, 변경자 ID, 이전 이름, 새 이름, 한국 시각을 저장한다. 변경자는 현재 본인만 사용한다. 조회 때 현재 닉네임을 조인해 과거 내용을 덮어쓰지 않는다. 기능 적용 이전의 이름·시각을 추측해 소급 생성하지 않는다.

## 개인정보

목록과 기본 상세는 필요한 회원·역할 표시 컬럼만 선택하며 비밀번호/연락처를 포함하지 않는다. 개인정보 기능 권한이 있는 관리자는 회원 정보 탭에서 원문 GET 경로를 자동 조회한다. 마스킹·열람 사유 입력·별도 원문 열람 버튼·자동 숨김은 제거했다. 미등록 값은 미등록으로 구분한다. 비밀번호·토큰은 어느 응답에도 조회하지 않는다.

`USER_SENSITIVE_VIEWED` 감사에는 열람 대상/필드 목록/버전만 남기고 사유는 null이다. 원문 개인정보와 인증 정보를 감사 detail에 복사하지 않는다. 감사 저장 실패 시 원문 응답을 반환하지 않는다. BFF는 공개할 계약 필드만 복사하고 no-store를 사용한다. 브라우저는 원문을 저장소에 보관하지 않고 모달 종료 시 상태를 해제한다. 기존 `USER_SENSITIVE_READ` 권한과 탈퇴 회원의 원문 조회 거절은 유지한다.

## 상태·역할·세션

역할 정책 행 → 행위자 행 → 대상 행 순서의 잠금과 최신 기능 검사를 사용한다. 상태는 기존 `UserService`의 Redis 차단/폐기/커밋 후 조건부 해제를 재사용한다. DB 또는 감사가 실패하면 변경은 롤백되며 먼저 차단한 Redis는 보안을 위해 차단을 유지할 수 있다. 이 경우 최신 내용을 조회한 뒤 ACTIVE를 재적용하면 기존 재활성화 절차로 복구한다. 이미 종료한 세션은 다시 살아나지 않는다.

일반 관리자는 SUPER_ADMIN의 세션을 종료할 수 없다. 최고 관리자의 상태·역할 변경은 거절하고, 본인의 비활성화도 Redis 부수 효과 전에 거절한다. SUPER_ADMIN은 자신의 모든 세션 종료를 명시적으로 실행할 수 있다. 탈퇴 복구·관리자 탈퇴 처리·가입대기 상태 생성은 이 단계에 추가하지 않는다.

역할 배정은 기존 `roleVersion`, 상태/세션/민감 열람은 새 `managementVersion`을 사용한다. `managementVersion`은 User의 JPA `@Version`으로 프로필·비밀번호·상태·역할 변경에도 증가해 오래된 편집을 구분한다. 충돌 409는 변경 요청을 자동 재전송하지 않으며 최신 정보를 다시 불러오게 한다. 기존 역할 API의 서버 사유 계약은 유지하되 UI에서는 사유를 필수로 입력한다.

## 적용

새 Flyway **V16**이 `tbl_user.management_version`, 회원 검색 인덱스, `tbl_user_nickname_history`를 추가한다. 기존 V1~V15는 수정하지 않는다. 백엔드를 재시작하면 기존 Flyway 설정으로 적용하고 Hibernate가 검증한다. 회원/비밀번호/현재 닉네임과 역할은 바꾸지 않으며 별도 초기 이력을 만들지 않는다. 프론트도 재시작/재빌드해 새 메뉴와 BFF 경로를 반영한다.

검증은 전용 임시 DB·Redis에서만 수행했다. 실제 local/dev/prod DB에 V16을 임의 적용하거나 실제 회원을 변경하지 않았다. 기존 `admin`의 SUPER_ADMIN 배정은 [별도 실제 배정 기록](super-admin-initialization-2026-10-24.md)을 유지한다.

후속 단계는 로그인·가입 등 활동 로그/관리자 감사 조회, 채팅 내역 조회, 지표 대시보드·서비스 상태다. 신고·제재, 공지 배너, 회원 메모, 내보내기, 방 강제 종료는 추가하지 않았다. [검증 결과](../../../artifacts/admin-development-stage5/verification.md)를 참조한다.
