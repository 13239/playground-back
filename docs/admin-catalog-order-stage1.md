# 게임·장르 관리 개선 1단계: 그리드 노출 순서

후속 [2단계](admin-catalog-grid-stage2.md)에서 번호 페이지 그리드·순서 변경 모드·상세 모달을 연결했다. 아래 순서 API는 유지하고 관리자 일반 목록과 장르 옵션 조회는 2단계 계약을 따른다.

게임·장르의 노출 순서를 그리드의 행 순서로 관리하기 위한 저장 구조와 API를 추가했다. 이번 단계에서는 기존 상세 폼의 노출 순서 입력도 제거한다. 그리드·드래그 모드·상세 모달·장르 콤보박스는 후속 화면 단계에서 연결한다.

## 순서와 일반 정보 저장 분리

- 게임과 장르의 `sort_order`는 전체 목록 기준 0부터 시작하는 연속 순번이다. 게임·장르의 일반 정보 저장 요청에서는 `sortOrder`를 제거했다. 수정 시 기존 순서를 보존하고 신규 등록은 끝에 추가한다.
- 게임 목록과 장르 목록은 각각 별도의 전체 순서 버전을 갖는다. 순서 저장과 신규 등록은 해당 버전을 올린다. 이름·공개 여부 등 순서와 무관한 수정은 전체 순서 버전을 올리지 않는다.
- 모드는 `GameModule.modes()` 정의 순서를 사용한다. 모드의 수동 순서 요청·응답·엔티티 필드와 DB 컬럼은 제거했다. 미지원 모드는 관리자 조회에서 뒤에 보존하고 공개 조회에서는 기존 지원 검증에 따라 제외한다.
- 공개 게임·장르 목록과 게임에 붙는 장르 라벨도 동일한 저장 순서를 사용한다. 숨김·비활성 항목은 전체 순서에는 포함하고 공개 경계에서 제외한다.

## 순서 편집 API

브라우저는 Next.js BFF의 동일한 경로를 호출한다. 기존 로그인·브라우저 증명·관리자 진입 및 기능 권한 검사를 그대로 적용하며, Spring API는 기존 BFF 인증을 추가로 요구한다. 응답은 캐시하지 않는다.

| 메서드 | 경로 | 기능 권한 | 용도 |
|---|---|---|---|
| GET | `/api/admin/games/order?page=1&size=20` | GAME_READ | 전체 게임 순서의 번호 페이지 |
| PUT | `/api/admin/games/order` | GAME_WRITE | 게임 행 이동 일괄 저장 |
| GET | `/api/admin/game-genres/order?page=1&size=20` | GAME_READ | 전체 장르 순서의 번호 페이지 |
| PUT | `/api/admin/game-genres/order` | GAME_WRITE | 장르 행 이동 일괄 저장 |

조회 조건은 `page`, `size`만 허용한다. `size`는 10·20·30·50이고 기본값은 20이다. 기본 페이지는 1이며 마지막 페이지를 넘는 요청은 현재 마지막 페이지로 보정한다. 빈 목록도 1페이지로 반환한다. 검색 결과의 일부를 전체 순서로 오인하지 않도록 검색·필터·커서는 받지 않는다.

조회 응답 예:

```json
{
  "items": [{ "code": "BOARD", "name": "보드", "sortOrder": 0, "version": 3 }],
  "page": 1,
  "size": 20,
  "totalPages": 1,
  "totalElements": 1,
  "version": 7
}
```

바깥 `version`은 전체 순서의 버전이고, 각 행의 `version`은 상세 정보 편집에 사용하는 행 버전이다. 여러 페이지를 불러올 때 전체 순서 버전이 달라지면 기존 편집 상태를 다시 확인해야 한다.

저장 요청 예:

```json
{
  "expectedVersion": 7,
  "moves": [
    { "code": "BOARD", "beforeCode": "PUZZLE" },
    { "code": "CASUAL", "beforeCode": null }
  ]
}
```

- `code` 행을 `beforeCode` 행 바로 앞으로 이동한다. `beforeCode`가 null이거나 생략되면 전체 목록 끝으로 이동한다.
- 이동은 배열 순서대로 적용하고 요청 전체를 한 번에 커밋한다. 다른 페이지의 행도 기준으로 사용할 수 있다.
- 페이지의 마지막 위치에 놓을 때 다음 페이지의 첫 행이 있다면 그 코드를 기준으로 사용한다. null은 현재 페이지 끝이 아닌 전체 목록 끝이다.
- 한 요청은 최대 100개 이동을 받는다. 같은 이동 대상 코드의 중복과 자기 자신을 기준으로 한 이동은 400으로 거절한다. 없는 대상·기준 코드는 해당 게임·장르 미존재 오류로 거절한다.
- 전체 순서 버전이 다르면 `GAME_CATALOG_CHANGED`/409를 반환한다. 모든 이동이 이미 해당 위치에 있는 요청은 버전과 감사 기록을 추가하지 않는다.
- 저장 응답은 `{ "version": 8 }` 형태다. 성공 후 목록을 다시 조회해 실제 위치·행 버전·페이지 수를 반영한다.

## 트랜잭션·성능·감사

쓰기 잠금은 기존 관리자 권한 정책 → 해당 목록의 순서 상태 순으로 획득한다. 순서 조회는 목록 상태를 먼저 공유 잠금해 MySQL 반복 읽기에서도 전체 버전과 행 순서의 시점이 어긋나지 않게 한다. 신규 등록도 같은 목록 쓰기 잠금을 사용한다.

전체 카탈로그를 브라우저로 전송하거나 엔티티 컬렉션을 로딩하지 않는다. 조회는 필요한 페이지의 코드·이름·순번·행 버전만 읽고, 이동은 영향을 받는 순번 구간을 SQL로 갱신한다. 범위 안의 행 버전과 수정 시각도 갱신해 오래된 상세 저장을 거절한다. 일반 정보·공개 상태·게임 장르 연결은 순서 저장에서 변경하지 않는다.

순서 변경은 `GAME_ORDER_UPDATED` 또는 `GAME_GENRE_ORDER_UPDATED`로 기록한다. 이동 요청 행의 전후 위치를 기록하며 감사 저장이 실패하면 순서 변경도 롤백한다. 기존 개별 `sortOrder` 감사 기록의 표시도 유지한다.

## 적용

프론트와 MVC 백엔드를 함께 반영한다. 백엔드 시작 시 Flyway V20이 실행되고 Hibernate가 스키마를 검증한다. 기존 V1~V19는 수정하지 않았다. V20은 기존 `sort_order, id` 상대 순서를 보존해 순번을 정리하고 관리자 정렬 인덱스·순서 버전 테이블을 추가하며 모드의 수동 정렬 컬럼을 제거한다.

기존 게임 카탈로그 안내의 수동 `sortOrder` 요청 예시는 이 문서의 분리된 계약으로 대체된다. 이번 작업에서는 실제 local/dev/prod DB에 V20을 직접 적용하거나 실행 중인 앱을 재시작하지 않았다.

## 검증

별도 임시 MySQL에서 Flyway V1~V20 적용과 스키마 검증, 페이지 간 이동, 동시 저장 충돌, 잘못된 후속 이동과 감사 실패 시 전체 롤백, 신규 등록의 끝 배치, 일반 수정의 순서 보존, 공개 목록 및 구현 모드 순서를 확인했다. 결과는 [검증 기록](../../../artifacts/admin-catalog-order-stage1/verification.md)에 남긴다. 새로 작성한 임시 테스트 코드는 검증 후 삭제한다.

잠금과 서비스 단위 트랜잭션 구성은 [Spring Data JPA 잠금 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html), [트랜잭션 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/transactions.html)를 확인했다. BFF는 설치된 Next.js의 Route Handler 문서를 확인해 기존 명시적 경로·입력·응답 검증 흐름에 통합했다.
